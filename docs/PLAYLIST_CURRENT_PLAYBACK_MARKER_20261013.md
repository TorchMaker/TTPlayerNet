# 多播放列表的当前播放标记修正

日期：2026-10-13。

## 1. 问题与原因

在多个播放列表中依次播放歌曲后，重建版会在每个列表保留一个“当前播放”箭头和高亮。根因在 `VisiblePlaylistPlayingRow()`：普通列表分支直接返回 `ActivePlaylist().PlayingRow()`，把每份列表保存的历史播放位置当成了实时播放状态。

历史行是正常数据，不能通过遍历清空所有其它列表的 `PlayingRow()` 来修复。它还参与上一首／下一首、列表切换后的定位、追加歌曲是否自动播放以及 TTBL 保存。

## 2. 5.7.9 原版依据

参考：[原版伪代码](../../reverse/decompiled/TTPlayer.exe.pseudo.c)。原 EXE SHA-256 为 `c7999ea5823469c1684148cac1bd196009824348ccac5cdd45978f8fb574e28c`。

| 原版位置 | 实际作用 |
| --- | --- |
| `00487C0D` | 歌曲行自绘调用 `0042D719`，据返回值选择播放高亮色，并在左侧六像素区域绘制箭头。没有直接用 `CPlayList +0x1c` 判定高亮。 |
| `0042D719` | 在临界区内读取 `CPlayItem +0x9c`，返回该运行时声音引用是否非空。 |
| `00452E5F` | 在同一临界区中替换曲目的声音引用。机器码明确把目标地址增加 `0x9c`，再调用 `004045F3` 的引用赋值／释放逻辑。 |
| `0045AD86` | 打开音频成功后的处理路径调用 `00452E5F` 关联当前声音对象。 |
| `0045B78E` | 收尾旧播放源时调用 `00452E5F` 清除引用。对应机器码在调用前执行 `xor edi, edi`，提供空的新引用。 |
| `0047FB0C` | 更新当前列表的 `+0x1c`，并刷新相关行；这是每份列表的历史请求行，可以在停止后保留。 |
| `0047F294` | 切换列表时分别处理 `+0x20` 的临时焦点行与 `+0x1c` 的历史行，说明它们与实时声音引用是三种不同状态。 |

因此，列表里保存历史位置，与正在播放的箭头／高亮需要分开。停止后仍能保留曲目信息和历史位置，不代表停止的曲目仍应绘制实时播放标记。

## 3. 修正实现

### 3.1 当前播放项只属于一个普通列表

`VisiblePlaylistPlaybackRow()` 将全局的 `playing_playlist_index_` 和 `current_` 映射到可见列表。只有播放所属列表与可见列表相同，才返回当前行。相同路径同时存在于多份普通列表时，也只标记实际所属的那份列表。

媒体库仍按曲目身份映射到当前查询结果中的行，避免把播放快照的行号套到另一种查询顺序上；普通列表不会借用媒体库播放快照的标记。

### 3.2 运行时标记与历史位置分开

`VisiblePlaylistPlayingRow()` 进一步检查：

- 当前源已成功打开。
- 状态为播放或暂停。
- 当前列表索引有效。
- 列表项与已打开源的路径、子曲目一致。

停止、打开中、打开失败、仅恢复选择而未开始播放、从列表移除当前项及无效索引均不绘制实时箭头。每份列表保存的历史行保留。

普通列表导航继续使用原有 `PlayingRow()`。媒体库导航及其“空闲时添加”的判断使用独立的身份映射，不受实时绘制标记是否存在影响。

### 3.3 统一绘制和刷新

原生皮肤的箭头／高亮、插件皮肤的 `TtpSkinState.playing_row` 都通过同一个实时标记方法取得结果。播放状态更新时比较上次可见标记，仅在变化时触发播放列表重绘，避免停止或切换源后留下旧像素。

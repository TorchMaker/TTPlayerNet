# 7z、TAR、GZ 音乐归档支持方案

日期：2026-10-12。本文件保留实施前的方案。**本轮已实现 TAR、gzip、tar.gz／tgz 和 7z，并补齐 UTF-8 ZIP／ZIP64；实际范围、只读依据和三系统测试见 [实施记录](ARCHIVE_EXTENSIONS_AND_READONLY_20261012.md)。**

## 1. 与 5.7.9 原版的关系

原版 EXE 的 `004738B5` 只分派 `.zip` 与 `.rar`，`00474051` 负责枚举、生成 `archive|member` 和展开 CUE。没有发现这条音乐归档流程使用 7z、TAR 或 GZ 的证据。因此它们属于新功能，不应列为原版遗漏功能，也不能只增加文件选择器的扩展名。

## 2. 三类格式需要不同的处理

| 格式 | 对播放器的意义 | 成员定位与缓存 | 包内 CUE |
| --- | --- | --- | --- |
| `.7z` | 多文件归档；要区分普通成员与固实压缩块 | 读取固实块中后面的文件可能要求解码前面的数据；限制字典、块大小和输出，支持取消 | 可沿用虚拟成员路径；同一音频对应多个 CUE 子曲目，共用成员存储 |
| `.tar` | 多文件归档，基本 TAR 本身不压缩；还要识别 ustar、PAX、GNU 长名称及稀疏项 | 普通连续成员可用有界文件区间直接读取；稀疏项需要逻辑长度映射或明确拒绝 | 适合直接读取相邻 CUE 和音频，索引必须记录真实成员名与偏移 |
| `.gz` | 通常是压缩一个字节流，不等于多文件归档目录 | 没有通用随机定位索引；前向解压到共享存储，回退读取已产生部分 | `song.flac.gz` 可表示一个音频流；单独 `album.cue.gz` 不会自动包含 CUE 引用的音频 |
| `.tar.gz`／`.tgz` | gzip 压缩层包裹 TAR 目录层 | 先经过 gzip，再按 TAR 成员边界消费；枚举可能需要走完压缩流 | 能包含完整专辑 CUE 和音频；应统一表示为 `album.tar.gz|disc\album.cue` |

zlib 官方说明 gzip 是面向单文件的压缩格式，并提供 gzip 流及完整性校验接口。不要把 gzip 的拼接流误当成带独立名称、可随机定位的 ZIP 式目录。[zlib 手册](https://zlib.net/manual.html)

7-Zip 的 C 解码接口文档描述了固实块输出缓冲区及其缓存。因此，直接把“一整个固实块放入内存”的示例接到 32 位播放器，会引入新的内存峰值。现有 ZIP／RAR 的小成员内存、大成员临时文件方案不能自动消除解码库内部的整块分配。[7-Zip C 解码接口](https://github.com/ip7z/7zip/blob/main/DOC/7zC.txt)

## 3. 后端选择

### 推荐：裁剪后的 libarchive，先接 TAR／GZ，再接 7z

libarchive 官方列出 TAR、PAX、GNU TAR、7-Zip 读取，以及 gzip 过滤器；它采用流式架构，支持 Windows／Visual Studio，静态链接时可裁剪模块。建议仅启用需要的读取器和压缩过滤器，关闭写入器、命令行工具及其他无关格式。**现有 ZIP 原版兼容规则和 UnRAR 后端继续保留**。[官方项目](https://github.com/libarchive/libarchive)、[架构和许可证](https://www.libarchive.org/)

主要收益是减少自行实现 PAX、长名称、校验和等格式细节的维护负担。成本是新增依赖及旧系统适配。官网“支持 Windows”不能代替 XP 结论：必须实际做 x86、VC-LTL、YY-Thunks 构建、导入审计和 XP／Win7 运行测试。DLL 体积也应由裁剪后构建测量，不预先承诺增量。

### 备选：LZMA SDK 加专用 TAR／gzip 读取器

适合以最小二进制和较窄格式范围为目标的实现。LZMA SDK 官方提供 ANSI C 的 7z 解码示例，采用公有领域授权；当前官网版本为 26.04（2026-10-05）。采用时应固定版本、校验源码哈希，并核对该版代码实际支持的方法与过滤器，不能把旧接口文档中的限制直接当成当前全部能力。[LZMA SDK](https://www.7-zip.org/sdk.html)

不过，自写 TAR 的长文件名、PAX 字段、稀疏文件与损坏输入处理，再改造 7z 整块缓存为可控输出，工作量较大。综合可靠性与后续维护，优先验证 libarchive 裁剪方案；如果实际体积或 XP 适配不合适，再评估此备选。

不建议依赖系统 `tar.exe`、Windows Shell 或外部 7-Zip 进程作为播放器常规解压路径。这些能力随系统和安装环境变化，也难统一共享任务、取消和错误返回。

## 4. 如何接入当前代码

1. **沿用 DLL 服务。** 在 `ttpcomm/src/archive_internal.h` 的 `Sink::Begin/Write` 后增加后端适配，继续使用 `archive_stream.cpp` 的成员存储、独立游标、取消、完成状态与缓存失效机制。
2. **明确格式能力。** 新增 capability 位并更新 SDK 检查；保持旧 ABI 1、ABI 2 已有函数和原 67 个导出兼容。所有新功能继续只读。
3. **统一路径与类型判断。** 扩展 `ArchiveKind`、`ParseArchiveMemberPath`、成员路径构建和文件导入；同时检查文件信息、封面、歌词、转换、CUE、最近文件与关联过滤器，避免各处分散判断 `.zip/.rar`。
4. **先识别容器，再枚举。** `.tar.gz` 作为一层音乐归档处理；普通 `.gz` 使用有明确命名规则的单成员模型。原始文件名提示缺失时，可从外层文件名去掉 `.gz`；名称只作为逻辑身份，不用于直接写磁盘。
5. **保持 CUE 路径规则。** 新格式可复用字面相对拼接及同名候选回退；不要顺便修改 ZIP／RAR 已恢复的 `..`、单斜杠、绝对路径语义。禁止无界递归打开嵌套压缩包。
6. **存储与取消先行。** 限制成员数、逻辑长度、字典和固实块资源；解析头、跳过前置块、解压和等待读取都须响应停止。解压校验未完成时仍标记待完成，不能把已产生全部字节等同于校验成功。
7. **许可证与构建。** 许可证保存在仓库；固定版本和 SHA256，构建时下载。实际发行所需声明按各依赖条款处理，不把完整许可证塞进 DLL 资源。

## 5. 建议实施和验收顺序

1. TAR 普通文件、ustar/PAX/GNU 长名称、Unicode 名称与 CUE；明确拒绝链接、设备项和未实现的稀疏变体。
2. gzip 单音频、`.tar.gz/.tgz`；校验 CRC、截断、多段 gzip 和取消，确认大文件不会整包驻留内存。
3. 7z 普通／固实、LZMA／LZMA2 等选定方法；密码、加密头、分卷与特殊过滤器逐项声明能力，未实现时返回明确错误。
4. 共用文件替换失效、多个读取者、最后一个读取者取消、CUE 切曲不重复解码、末尾失败和退出清理测试。
5. 比较压缩包内外的完整 PCM、分轨边界、Seek、元数据及封面；完成 Windows 11、XP、Win7 验证。Windows 11 作为用户指定的现代系统代表，不能记录成执行过真实 Windows 10。

原版对照用于继续验证共同的 CUE、列表和 Reader 行为；原版本身没有这三种归档入口，不能把“原版播放新格式失败”作为新后端的兼容性失败。

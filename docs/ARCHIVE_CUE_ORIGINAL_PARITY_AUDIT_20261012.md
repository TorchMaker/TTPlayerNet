# ZIP／RAR 内 CUE 与 5.7.9 原版的差异审计

日期：2026-10-12。重建版核对基线：`6e8481e`。

> **修复状态：第 8 节建议中的成员身份、CUE 路径、共享缓存、后台读取与取消已完成，原版 EXE 对照及 XP／Win7 回归已执行。本文保留修复前审计记录；当前实现、实测结果和仍保留的差异见 [修复实施记录](ARCHIVE_CUE_RECOVERY_20261012.md)。**

本文比较的是**当前重建版与 5.7.9 原版伪代码、二进制的差异**。ZIP 与 RAR 之间的不同仅用于说明各自的原版路径；现代归档格式扩展不作为“原版已有而重建遗漏”的功能。

原版依据：仓库根目录 `TTPlayer.exe` 及 `reverse/decompiled/TTPlayer.exe.pseudo.c`。本次二进制 SHA256 为 `c7999ea5823469c1684148cac1bd196009824348ccac5cdd45978f8fb574e28c`。函数地址比伪代码文件行号更稳定，以下同时列出关键地址和当前源码位置。

首次审计只增加分析文档和本地专项测试；随后按用户要求完成生产修复及 Actions 组件要求更新。测试代码、样本和记录保留在私有 `tests/archive_support/cue_audit_20261012/`，不进入 Actions 或发行包。

## 1. 修复前结论

**ZIP、RAR 包内 CUE 的正常导入、分轨和播放路径已经实现，但归档成员读取机制及部分路径边界尚未完全恢复原版。**

目前最值得优先修复的是：

1. ZIP 在按宽字符找到成员后，又按原始字节重新查找；某些中文名称会混淆，实际读到另一个成员。已在本机复现。
2. CUE 的单个前导斜杠、相对形式的显式归档路径，与原版的绝对路径判定和字面拼接不同。
3. 原版有“当前成员共享缓冲”及后台解压、按已产出字节读取、取消机制；重建版每次打开都先完整取得成员，尚未接齐这些行为。
4. ZIP 音乐读取复用了皮肤包读取器，内存使用、解压结束判定与原版音乐读取器不同。

RAR 已在上一轮迁移到 `ttpcomm.dll` 的 UnRAR 引擎，**当前不再依赖 Windows Shell 解压**。旧文档中的 Shell、字母排序、整包落盘等描述只代表迁移前状态。

## 2. 原版如何处理包内 CUE

### 2.1 导入

`004738B5` 根据扩展名创建 ZIP 或 RAR 对象。`00474051` 从归档对象虚表 `+0x0C` 枚举成员，按成员顺序处理：

- 普通音频生成 `外层压缩包|成员` 逻辑路径，再按已注册的音频类型筛选。
- `.cue` 通过虚表 `+0x14` 读到内存，连同逻辑路径交给 `00473EC5`。
- `00473EC5` 为每个解析出的曲目生成一行，子曲目编号按解析后的顺序从 1 开始。

例如包中有 `Disc1\album.cue`，里面两首歌共用 `image.flac`：

```text
播放列表第 1 行：Album.zip|Disc1\album.cue，subtrack = 1
播放列表第 2 行：Album.zip|Disc1\album.cue，subtrack = 2
实际音频成员：  Album.zip|Disc1\image.flac
```

CUE 行保存的是 CUE 身份及子曲目编号，不是临时解压文件名，也不是预先切出的两个音频文件。重建版目前沿用这套结构。

### 2.2 打开与定位

`004E323B` 重新读取 CUE、选择子曲目，再打开 `FILE` 指向的音频：

1. `004E31EE` 判断 `FILE` 是否为绝对形式。
2. 相对路径按 CUE 所在目录字面拼接；归档内保留 `archive|member` 结构。
3. 首选音频打开失败后，依次尝试 CUE 同名且沿用原扩展名、`.ape`、`.tak`。
4. 通过对应音频 Reader 定位到曲目起点，并限制读取边界。

重建版的 `CueSheet::AudioCandidates` 和 `CueSegmentSource` 已实现这条主路径。音频格式仍取决于可用 Reader；解压成功不代表任何成员都能解码。

### 2.3 成员缓冲与后台读取

这是目前差异较大的部分：

- `004DFBF9` 为目标成员建立分页文件支持的映射，并登记解压回调 `004DFD8E`。
- `004DFDED` 在临界区内比较逻辑成员路径；当前对象同名时复用，不同名时释放管理器持有的旧对象并建立新对象。
- `004C4A6D` 打开归档流时进入上述共享对象路径。
- `004C4CA8` 根据已产出字节数决定能否读到请求区间；数据不足时以 200 ms 为间隔等待，并检查取消事件与超时。
- ZIP 的 `0041F0F2`、RAR 的 `0047366F` 设置取消标志并等待工作线程退出。

因此原版具备“解压尚未完成时，Reader 可以读取已完成区间”的结构。它仍为整个成员预留映射，不能称为完全不保存成员内容的纯流式读取。现有证据也只支持当前成员复用，不能扩张为多压缩包无限缓存或多线程预取队列。

## 4. 确认存在的差异

### 4.1 ZIP 中文成员名可能匹配到另一个文件

原版 `0047E177` 与 ZIP 查找函数 `0041F5BA` 使用宽字符名称和 `_wcsicmp`。ZIP 原始名称先通过 `OemToCharBuffW` 转为宽字符。

当前 `src/audio/archive_member.cpp:124` 的流程却是：

1. `DecodeZipMemberName` 按 OEM 代码页解码。
2. `_wcsicmp` 找到正确的 `SkinEntry`。
3. 调用 `package.ReadEntry(entry.name, ...)`，再次搜索原始字节名称。
4. `src/skin/skin_package.cpp:29` 的 `SameEntryName` 逐字节调用 `_strnicmp`。

中文双字节编码的第二字节可能恰好处于 ASCII 字母区间。逐字节忽略大小写会把不同汉字当成同一个文件名。

本机 OEM 936 样本：

| 成员 | 原始名称前两字节 | 内容 |
| --- | --- | --- |
| `丄.wav` | `81 41` | 第一份数据 |
| `乤.wav` | `81 61` | 第二份不同的数据 |

请求第二个成员时，实测返回第一份数据。日志为 `second member returned first bytes=1 returned intended bytes=0 OEM=936`。

影响不仅是显示乱码，还可能出现“所选曲目与实际读取内容不一致”。ZIP CUE 导入也使用 `ReadEntry(entry.name, ...)`，同类名字的 `.cue` 成员同样存在这条风险路径。

**建议：匹配成功后直接读取已经找到的成员记录或索引，去掉二次字节名称查找。** 已有 `ReadEntry(const SkinEntry&, ...)` 可用。保留原版的宽字符忽略大小写语义。这个问题与是否增加 UTF-8 ZIP 支持是两件事。

证据等级：重建版错误已复现；原版宽字符查找由伪代码确认，本轮没有运行原版样本。

### 4.2 CUE FILE 的特殊路径分类不同

`004E31EE` 要求长度至少 3，再识别盘符加冒号、双反斜杠、或位于开头之后的 `://`。它没有“看到 `.zip|`／`.rar|` 就视为绝对路径”的规则，也不把单个前导斜杠作为归档根。

以 `A.zip|disc\album.cue` 为来源：

| FILE 内容 | 原版伪代码行为 | 当前重建版行为 |
| --- | --- | --- |
| `image.wav` | 拼接 CUE 成员目录 | `A.zip|disc\image.wav`，对应 |
| `..\image.wav` | 字面拼接，不消去 `..` | `A.zip|disc\..\image.wav`，对应 |
| `\image.wav`（一个前导反斜杠） | 仍属相对值，保留 CUE 目录并字面追加 | 去掉前导符，改为 `A.zip|image.wav` |
| `other.zip|image.wav` | 不满足绝对判定，仍追加在当前 CUE 目录后 | 直接视为另一份相对路径归档 `other.zip` |
| `D:\other.zip|image.wav` | 盘符绝对形式 | 直接使用，对应 |
| UNC 或正常 `http://...` | 绝对形式 | 正常形式对应；畸形形式未穷举 |

表中原版特殊路径是对判定和拼接代码的静态推导，最终是否打开还受同名候选回退影响。本轮实测确认了重建版的三个特殊路径输出，没有把它们记为原版运行结果。

当前 `cue_sheet.cpp:87` 关于“显式虚拟成员已经完整”的注释范围过大；绝对外层归档路径与相对 `other.zip|...` 应分开。

**建议：恢复原版的绝对判定和字面拼接规则，并为单前导符、双前导符、盘符、URL、相对显式归档分别建立对照样本。** 不要统一使用 `lexically_normal()` 把原版未解析的 `..` 自动消掉。

RAR 还存在另一层有意限制：`ttpcomm/src/archive.cpp:213` 拒绝成员名中的 `.`／`..`、根路径、盘符和链接。即使原版可能按字面匹配这些异常成员，也不建议直接取消保护；需要把兼容名称与禁止落盘路径分层考虑。

### 4.3 尚未恢复当前音频成员的共享缓冲

原版 `004DFDED` 复用当前同名成员对象。重建版 `OpenArchiveMemberStream` 每次打开都新建存储：

- ZIP 重新打开外层包并解压目标成员。
- RAR 重新枚举并解压目标成员；固实包还可能处理其前序数据。
- `CueSegmentSource::Open` 每个子曲目会重新读 CUE，并打开对应音频。
- 后台信息读取也会为每个子曲目探测对应音频。

因此同一整轨镜像的多个 CUE 子曲目可能反复解压同一个大文件。当前 RAR `IStream::Clone` 能共享一个已打开流的存储，但播放器没有用它建立跨打开操作的成员复用；只有这个接口不等于已经恢复缓存。

**区分 Seek 和切歌：同一已打开曲目内的 Seek 使用现有成员流，不会每次拖动都重新解压。缺口主要在重新打开、子曲目切换及信息读取。**

建议先恢复有容量限制的当前成员复用，缓存身份包含外层包路径、文件变化信息及成员身份，避免包已修改后仍读取旧数据。没有必要先做超出原版范围的无限缓存或并行预取。

### 4.4 后台解压、按可读区间等待和取消尚未接齐

当前 ZIP 完整解压到 `vector` 后复制为 `HGLOBAL IStream`；当前 RAR `OpenMember` 在 `RAR_TEST` 完成、长度及校验通过后才返回流。

这与原版 `004C4CA8` 等待“当前请求区间已解压完成”不同。大成员即使头部已经够 Reader 识别，也要等整个成员处理完成才能进入解码。

RAR DLL 已具备进度／取消回调，甚至可取消等待引擎锁和固实前序处理；但：

- 播放器 `OpenArchiveMemberStream` 传入空 options。
- CUE 的 `ReadArchiveMember` 只设置成员大小上限，没有传取消回调。
- ZIP 当前解压路径没有对应的取消检查。

播放工作线程已经有停止标志和部分 I/O 取消机制，不能据此断言“点击停止一定卡住界面”。准确缺口是：归档解压本身没有稳定地消费播放停止信号，旧任务可能继续占用 CPU、存储或阻塞后续成员打开。

**原版导入 CUE 时也使用同步读取（`00474051` 的最后参数为 0）**。不能把“导入时读取 CUE 可能等待”单独称为重建遗漏；需要恢复的主要是播放成员的任务、进度、等待和取消生命周期。将初次导入也全面异步化属于进一步优化。

建议分两步：先将取消和进度接到现有后端；再设计可共享的后台成员任务及区间等待。若允许校验前读取，必须同时设计末尾校验失败的传播，保留现有完整性校验能力。

### 4.5 ZIP 音乐读取误用了皮肤读取路径的部分语义

本次从原版 EXE 直接读取 `0x0051BF70` 虚表：

| 偏移 | 函数 |
| --- | --- |
| `+0x0C` | `0041EF26`，枚举 |
| `+0x10` | `0041F04D`，登记回调 |
| `+0x14` | `0041F061`，成员读取 |
| `+0x18` | `0041F0F2`，取消 |

结合构造函数 `0041ECD1`，可确认 `00474051` 的 CUE 读取和归档成员流走 `0041F061` → `0041F185`。后者用两个 16 KiB 缓冲循环读取、inflate、通知进度，并要求最终结果为 `Z_STREAM_END`。

`0041F422` → `0041F481` 则是另一条一次性读取路径，明确处理 Stored／Deflate，并允许单次 inflate 在给定输出长度下返回 `Z_OK`。皮肤包现有实现保留后者，是为了兼容真实旧皮肤样本。

当前音乐 ZIP 复用 `SkinPackage::ReadEntry`，因而：

- 没有原版音乐读取的分块进度与取消检查。
- 满足预期输出长度的 `Z_OK` 可以被接受；原版音乐路径要求 `Z_STREAM_END`，损坏／截断边界可能不同。
- 当前 Stored ZIP 样本可正常读取，但原版音乐 `0041F185` 中没有看到 Stored 直接复制分支。不能仅凭皮肤路径宣称原版音乐支持完全相同的方法集合。

**原版 Stored 音乐 ZIP 的实际结果仍需专门运行对照。** 本次确认了虚表和调用路径，没有把静态疑点写成已实测的原版失败。ZIP 注释尾部、自解压前缀也应分别验证。

建议归档层分离“皮肤一次性读取语义”和“音乐成员任务语义”。不要为了修音乐而直接改变全部皮肤读取器的 `Z_OK` 接受规则。

### 4.6 ZIP 额外内存占用不同

原版 `0041ED9D`／`0041EE29` 主要载入中央目录，文件内容通过句柄分块读；目标音乐成员保存在共享映射中。

重建版 `SkinPackage::Open` 载入整个外层 ZIP，然后生成完整成员 vector；返回后又复制到 HGLOBAL：

| 阶段 | 当前主要占用 |
| --- | --- |
| 解压成员时 | 整个外层 ZIP 数据 + 完整目标成员 vector |
| 创建音频流时 | 成员 vector + HGLOBAL 中的另一份成员数据 |

外层包在 `ReadZipMember` 返回时已经释放，不能把上述三份简单相加作为必然同时存在的峰值；但任一阶段都可能对 32 位进程造成较大压力。切换 CUE 子曲目又重复这些分配。

RAR 已采用小成员内存、大成员临时文件的后备存储，不存在同样的整包载入问题；这一改进可用于统一音乐归档流，而无需照搬原版 32 位映射大小限制。

### 4.7 成员类型筛选存在差异

原版 `00474051` 排除注册的列表格式后，按注册音频格式决定是否入表，没有当前这组硬编码的 `.cda/.mid/.midi/.rmi` 排除。

重建版在 ZIP 和 RAR 导入中明确跳过它们，原因是现有设备／MIDI 后端依赖文件名，不能直接消费归档流。

这是**筛选规则和后端能力的差异**。尤其 MIDI 需要继续对照原版的成员流能力。它不构成“原版包内任意 MIDI 已在本轮播放成功”的证据；CDA 依赖光盘，本来也不能把一个压缩后的 `.cda` 文件当作音频数据。

建议先确认对应原版 Reader 接口及实际支持，再按 Reader 能力恢复；不要只移除扩展名过滤而留下必然打不开的列表行。

## 5. 当前可见限制，但原版完整交互仍需进一步对照

这些项目不能全部直接标为“原版功能遗漏”：

| 项目 | 当前事实 | 仍需确认 |
| --- | --- | --- |
| 错误传播 | ZIP 导入异常和单个 CUE 异常可能被跳过；CUE 打开把密码／CRC／读取异常合并为解析失败 | 原版对应错误文字、提示时机、后续播放状态；后端失败回调已确认存在，不等于已确认其全部 UI |
| 密码输入 | RAR DLL 有密码参数，播放器尚未接密码输入 | 原版播放器是否暴露完整交互，不能因底层支持就假设原版 UI 一定支持 |
| 初次信息显示 | 包内 CUE 立即带入标题等字段，但时长先设为 `-2`，后续信息读取再补全 | 各种“添加时读取信息”选项下，与原版的初次标题、时长及读取时机逐项对照 |
| 重复行 | 原版归档导入按播放项身份去重；CUE 分轨和音频整轨身份不同 | 相同包反复导入、同名成员、大小写变化、不同入口的去重范围 |
| CUE 引用音频也单独入表 | 当前按成员循环，可能同时出现 CUE 分轨及完整音频 | 原版也有独立成员分支；没有证据支持把所有整轨行自动隐藏作为复原要求 |
| 封面与增益写入 | 包内 CUE 只读，信息读取不继承源音频封面 | 原版包内 CUE 封面行为未完成专门对照；不能把写回 ZIP／RAR 当作原版已具备能力 |

已有音频解码支持不等于归档内所有辅助文件的自动关联都已验证。外置歌词、图片、混合多 FILE CUE、重启后恢复等应单列测试，不以常规 CUE 样本代替。

## 6. 应保留的改进与原版本身的限制

| 项目 | 与原版的关系 | 建议 |
| --- | --- | --- |
| RAR5 | 原版旧引擎不支持；当前 UnRAR 支持 | 保留，属于扩展 |
| RAR 大成员磁盘后备、64 位流长度 | 原版主要为 32 位成员大小及映射 | 保留，属于改进 |
| RAR 字典、成员、条目限制及链接过滤 | 新后端增加明确资源和名称限制 | 保留；兼容边界可细化，不直接删除保护 |
| UTF-8 无 BOM CUE | 原版检测为 UTF-8 后存在无条件跳过 3 字节的问题 | 不恢复丢字节缺陷；当前解析改进保留 |
| ZIP OEM 名称 | 原版使用 OEM，当前音乐 ZIP 也使用 OEM | 基础编码选择对应；第 4.1 节的二次查找错误仍须修 |
| UTF-8 ZIP、ZIP64、AES、更多方法 | 未见原版音乐完整支持的证据；当前音乐 ZIP 也未补齐这些扩展 | 单独规划，不能列为原版复原缺口 |
| ZIP CRC | 当前音乐 ZIP 未校验 CRC；所核对原版 ZIP inflate 路径也未见 CRC 比较 | 可以加固，但不能写成“原版有而重建漏掉” |
| 严格 ZIP 本地头／中央目录一致性检查 | 当前增加名称、标志、方法、大小及边界校验 | 保留；畸形包与原版不同是有意差异 |
| 包内标签、CUE、封面写回 | 原版归档读取链没有完整重新打包提交协议 | 维持只读；写入应另立功能和可靠保存方案 |
| 7z／TAR 及嵌套包 | 原版音乐导入并未普遍支持 | 不是此次复原的必需项 |

## 8. 建议修复顺序

1. **先修 ZIP 成员身份。** 取消二次字节名称查找，覆盖普通音频、包内 CUE 和信息读取；验证中文双字节、大小写及分隔符。
2. **修 CUE 路径判定，并确认 ZIP 音乐读取的结束条件。** 以 `004E31EE`／`004E323B` 和音乐虚表调用链为准，保留皮肤自身规则；先补原版边界运行样本。
3. **统一可复用的音乐成员存储。** ZIP 避免整包载入及多余整成员复制；ZIP／RAR 为当前成员共享存储，给 CUE 子曲目和元数据读取独立游标，加入文件变化失效规则。
4. **接齐停止、进度和后台区间读取。** 先传递取消，再恢复可等待的后台任务；同时处理错误、末尾校验、流释放及退出，保留 RAR 现有校验和大成员后备。
5. **补交互及格式能力对照。** 处理包内 CUE 错误信息、初次元数据显示、去重、MIDI 能力和异常包；按实际 Reader 能力恢复导入规则。
6. **最后安排现代 ZIP 扩展。** UTF-8、ZIP64、CRC 加固、加密等明确标为新增能力，与 5.7.9 行为恢复分别验收。

前四项完成后再执行原版、Windows 11、XP、Win7 的统一样本矩阵。当前结论是“常规包内 CUE 主链路已具备，成员身份与读取生命周期尚有实质差异”，不是“CUE 未实现”，也不是“已完全与原版一致”。
